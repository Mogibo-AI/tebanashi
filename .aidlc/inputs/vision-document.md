# Vision Document — Tebanashi（手放し）

## Executive Summary

Tebanashi は、合わない習慣・サブスク・継続コミットメントを「賢明な損切り」として手放せるよう支援する、個人向けWebアプリケーションです。日本のChromeユーザーを主対象とし、独り言レベルの音声入力で「やめたいこと」を構造化し、ワンタップで手放し宣言できるとともに、AIが手放しを全肯定し、浮いたリソースの再投資先を提案します。継続を強迫的に美化する文化に対し、手放しを「失敗」ではなく「リソース最適化」へ再フレーミングすることで、ユーザーの精神的負荷の軽減と自己肯定感の向上を実現します。

## Business Context

### Problem Statement

現代の日本人ユーザーは、ジム会員、オンライン講座、習い事、サブスクリプションサービスなど、過去の自分が始めた多数のコミットメントを「やめられない」状態で抱えています。背景には、(1) サンクコストへの執着、(2)「継続は美徳」という文化的圧力、(3) 解約手続きの心理的・物理的な摩擦、(4)「やめる」ことを正当化するナラティブの不在があります。結果として、月数千〜数万円の継続支出と、月20〜40時間の精神的拘束時間が浪費されています。新しい習慣の挫折率は約95%という研究もあり、大半の人にとって継続は不自然な負荷ですが、それが個人の能力不足のように扱われています。

### Business Drivers

- **市場の変化**: サブスク疲れ・コミットメント疲れが社会的に顕在化している。
- **AIによるパーソナル支援の普及**: 生成AIにより、低コストで個別文脈に応じた肯定的フィードバックを提供できるようになった。
- **メンタルヘルス領域の拡大**: 自己肯定感・幸福度を扱うアプリ市場が拡大している。
- **タイミング**: Amazon Bedrock 上で十分な日本語性能を持つClaudeモデルが利用可能となり、低レイテンシで構造化と自然な日本語生成が両立できるようになった。

### Target Users and Stakeholders

| User Type | Description | Primary Need |
|-----------|-------------|--------------|
| 継続疲れ層 | 20〜40代の日本人個人ユーザー。ジム・サブスク・習い事・SNSなど複数のコミットメントを抱え、惰性で続けている自覚がある。 | 罪悪感なく「やめる」ための心理的後押し |
| 自己肯定感強化希望層 | 自分の決断を肯定してくれる外部装置を求める層。 | AIによる無条件肯定と賢明な決断としての再フレーミング |
| サンクコスト捕囚層 | 過去の投資を惜しんで惰性継続している層。 | サンクコストを切り離す合理的論拠と背中押し |

### Business Constraints

- **プラットフォーム**: Webアプリのみ。サポート対象ブラウザは Google Chrome 最新版に限定（MVP）。
- **言語**: 日本語UIのみ（MVP）。
- **リージョン**: 東京リージョン (ap-northeast-1) を中心に構築。
- **課金**: MVPは完全無料。決済機能は実装しない。
- **ホスティング/インフラ**: AWSサーバーレス構成を必須とする（運用コストを最小化するため）。
- **個人情報**: ユーザーが入力する内容には個人的な悩み・支出情報が含まれる可能性があり、最小限のデータ収集とプライバシー配慮が必要。認証はGoogleアカウントを利用するため、IdPから取得するプロフィール情報は必要最小限（ユーザー識別子・メールアドレス）に限定する。

### Success Metrics

| Metric | Current State | Target State | Measurement Method |
|--------|--------------|--------------|-------------------|
| 音声入力成功率（テキスト構造化まで完走） | 0 | 90%以上 | アプリ計装イベントによる成功/失敗ログ |
| 平均応答レイテンシ（音声入力後の構造化完了まで） | - | p95 で 8 秒以内 | CloudWatch メトリクス |

## Full Scope Vision

### Product Vision Statement

Tebanashi は「やめる」を文化として定着させるプラットフォームになる。継続の呪縛から解き放たれた個人が、自分の人生のリソース（時間・金・精神）を能動的に再配分する選択肢を当然のものにし、手放しの物語が共有・称賛される世界を作る。

### Feature Areas

#### Feature Area 1: 音声駆動の構造化（Voice Intake）

- **Description**: 独り言レベルの音声入力を、AIが「目標／想定コスト／リスク／手放し時のリターン」へ自動構造化する。
- **Key Capabilities**:
  - 日本語音声のリアルタイム文字起こし
  - LLMによるやめ候補の構造化（タイトル・カテゴリ・推定時間コスト・推定金銭コスト・手放した時の解放リソース）
  - 入力テキストへのフォールバック（音声が使えない環境向け）
- **User Value**: 「考えてからまとめる」というステップを排除し、思考の摩擦をゼロにする。

#### Feature Area 2: ワンタップ手放し（1-Tap Withdrawal）

- **Description**: 巨大な「手放す」ボタンを1回押すだけで手放し完了。言い訳・理由入力は不要。
- **Key Capabilities**:
  - 「手放す」ボタンUI
  - やめ候補のアーカイブ化
  - 手放しタイムスタンプ記録
- **User Value**: 「やめる手続き」の心理的摩擦を最小化する。

#### Feature Area 3: AIによる全肯定（AI Affirmation）

- **Description**: 手放しを英断として称賛する祝祭的フィードバック。
- **Key Capabilities**:
  - LLMによる手放し称賛メッセージ生成（やめ候補の内容に応じてパーソナライズ）
  - 浮いたリソースでの「最高のご褒美」提案
  - カジノ風のド派手な祝祭演出（アニメーション・効果音）
- **User Value**: 手放す苦渋を「賢明な決断をした誇り」に変換する。

#### Feature Area 4: リソース解放ダッシュボード（Phase 2想定）

- **Description**: 手放しによって解放された時間・金額の累計可視化。
- **Key Capabilities**:
  - 累計解放時間／金額の表示
  - 解放リソースの再投資ログ
  - 月次振り返りレポート

#### Feature Area 5: 手放しコミュニティ（Phase 3想定）

- **Description**: 手放しを共有・称賛し合う匿名コミュニティ。
- **Key Capabilities**:
  - 手放しストーリーの匿名投稿
  - 「いいね」「拍手」相当のリアクション
  - 月間ベスト手放しランキング

### Integration Points

- **Amazon Bedrock**: 構造化と肯定メッセージ生成のためのLLM呼び出し。
- **Amazon Transcribe Streaming**: 日本語音声のリアルタイム文字起こし。
- **（将来）外部カレンダー連携**: 解放時間の再投資を支援。
- **（将来）銀行口座/家計簿サービス連携**: 解放金額の自動集計。

### User Journeys (Full Vision)

#### Journey 1: 思いつきから手放しまで

1. ユーザーがアプリを開き、マイクボタンを押す
2. 「最近ジム行ってない、もう月8000円もったいないかも…」と独り言する
3. AIが「ジム継続をやめる」「想定解放: 月8,000円・月8時間」というやめ候補を生成
4. ユーザーがやめ候補を確認し、「手放す」ボタンをタップ
5. 派手な祝祭演出と共に「英断です。月8,000円と8時間が戻ってきました」と表示
6. AIが「浮いた8,000円で、ずっと気になってた本3冊どうでしょう」と提案
**Outcome**: ユーザーは罪悪感なく手放し、再投資先のヒントを得る

#### Journey 2: 過去の決定の整理

1. ユーザーが現在抱えているコミットメント（サブスク等）を一覧で振り返る
2. それぞれをやめ候補として登録
3. 一つずつ「続ける／やめる」を判断
4. やめると決めたものについてワンタップで手放す
**Outcome**: ユーザーは抱えている全コミットメントを能動的に整理する

#### Journey 3: 手放しの振り返りとシェア（Phase 3）

1. ユーザーが月次振り返りを開く
2. 今月手放した項目と解放リソース合計を確認
3. 印象的な手放しをコミュニティに匿名投稿
4. 他ユーザーから称賛リアクションを受け取る
**Outcome**: 手放しが個人的成功体験から社会的承認へ昇華する

### Scalability and Growth

- **ユーザー層拡大**: 個人ユーザーの規模拡大に応じてDynamoDBオンデマンド／Lambda同時実行をスケール。
- **デバイス拡大**: Web（デスクトップ／モバイルChrome）→ ネイティブモバイルアプリ（Phase 3）→ ブラウザ拡張（任意）。
- **データ拡大**: 手放し履歴を集約し、領域別の「やめてよかった度」統計を提供。

### Long-Term Roadmap

| Phase | Focus | Timeframe |
|-------|-------|-----------|
| MVP | Voice Intake + 1-Tap Withdrawal + AI Affirmation（Webアプリ／デスクトップ＋モバイルChrome、無料） | 初回リリース |
| Phase 2 | リソース解放ダッシュボード、月次振り返り、データ永続化強化 | MVPリリース後3〜6ヶ月 |
| Phase 3 | 手放しコミュニティ、ソーシャル連携認証、ネイティブモバイルアプリ展開 | MVPリリース後6〜12ヶ月 |
| Phase 4 | 外部連携（カレンダー・家計簿）、手放し統計の可視化高度化 | 1年以降 |

## MVP Scope

### MVP Objective

「独り言レベルの音声入力 → AI構造化 → ワンタップ手放し → AI全肯定」というコア体験が、日本語ユーザーにとって摩擦なく成立し、継続的に使用したくなる強度を持つことを検証する。

### MVP Success Criteria

- [ ] ユーザーがChromeブラウザ（デスクトップまたはモバイル）で音声入力を行い、5秒以内に構造化されたやめ候補が画面に表示される（p95）
- [ ] ユーザーがやめ候補に対して「手放す」ボタンをタップしてから3秒以内に祝祭演出と肯定メッセージが表示される（p95）
- [ ] 一連のフロー（音声入力→手放し完了）の成功率が90%以上（デスクトップ／モバイル双方で計測）
- [ ] 初回利用ユーザーがGoogleログイン後、追加の入力なくコア体験に到達できる

### Features In Scope (MVP)

| Feature | Description | Priority | Rationale for Inclusion |
|---------|-------------|----------|------------------------|
| 音声入力（日本語） | Chromeのマイクから音声を取得し、Amazon Transcribe Streamingで日本語をテキスト化 | Must Have | コア体験の入口。摩擦ゼロ入力の根幹 |
| AIによるやめ候補の構造化 | テキストをBedrock経由のClaudeで「タイトル／カテゴリ／推定時間コスト／推定金銭コスト／手放した時の解放リソース」に構造化 | Must Have | 「思考を止める」ためのコア機能 |

| AIによる全肯定メッセージ | やめ候補の内容に応じた肯定メッセージとご褒美提案を生成 | Must Have | 手放し体験の感情的価値の核 |

### MVP User Journeys

#### Journey 1（MVP）: 初訪問から最初の手放しまで

1. ユーザーがChromeでTebanashiのURLを開く
2. 「Googleでログイン」をタップ
3. IdPの認可画面で同意し、アプリへ戻る（Cognito User Poolが裏でユーザー作成）
4. ユーザーがマイクボタンをタップし、独り言する
5. AIがやめ候補を生成して表示
6. ユーザーが「手放す」ボタンをタップ
7. 祝祭演出と肯定メッセージが表示
**Outcome**: 数タップでログインを終え、初訪問から数分以内に最初の手放し体験を完了する
**Limitation vs Full Vision**: 累計可視化なし、コミュニティ機能なし、リソース提案は単発のみ

#### Journey 2（MVP）: 再訪問→過去のやめ候補からの手放し（任意の端末から）

1. ユーザーが任意のChrome（同一端末でも別端末でも可）でアプリを開く
2. 既ログインなら自動セッション復元、未ログインなら同じソーシャルログインでサインイン
3. 過去に作成したやめ候補の一覧が表示される
4. ユーザーが既存やめ候補を選び、「手放す」ボタンをタップ
5. 祝祭演出と肯定メッセージが表示
**Outcome**: 過去の登録項目を任意の端末から手放しに持ち込める
**Limitation vs Full Vision**: 累計可視化や月次振り返りはまだ提供されない

### MVP Constraints and Assumptions

- **Assumption**: ChromeのWeb Audio APIで取得した音声を WebSocket で Amazon Transcribe Streaming にリアルタイム送信する構成で、p95 5秒以内のテキスト化が実現できる（デスクトップ／モバイルChrome双方）。**Risk if wrong**: アーキテクチャ再設計（録音→バッチTranscribeに切替）が必要となりレイテンシが悪化する。
- **Assumption**: Amazon Bedrock の Claude モデルで、日本語の独り言から十分な精度でやめ候補の構造化ができる。**Risk if wrong**: プロンプト改善・モデル変更・後処理ロジック追加が必要。
- **Assumption**: ターゲットユーザー（日本のChromeユーザー）の大半がGoogleアカウントを保有しており、Googleログインによる初回オンボーディングの摩擦は許容範囲に収まる。**Risk if wrong**: Googleアカウントを持たないユーザーが離脱する。MVPでは許容し、Phase 2以降で別IdP（Apple等）の追加を検討する。
- **Assumption**: モバイルChrome（Android / iOS）でも、デスクトップChromeと同等の Web Audio API ／マイク権限挙動が得られる。**Risk if wrong**: iOS Chrome は WebKit ベースで挙動が異なるため、追加の互換対応や代替手段（ファイル入力フォールバック等）が必要となる。
- **Accepted Limitation**: Googleアカウントを持たないユーザーはMVPでは利用不可。
- **Accepted Limitation**: Chrome以外のブラウザ（Safari／Firefox／Edge等）はサポート対象外。アクセス時に案内を表示。
- **Accepted Limitation**: 推定時間／金銭コストはAIの推論結果であり、ユーザー個別の実コストとはズレうる。

### MVP Definition of Done

- [ ] すべての Must Have 機能が実装され、自動テストでカバーされている
- [ ] 音声入力→構造化→手放し→肯定メッセージのE2Eフローが90%以上の成功率で動作する（デスクトップChrome／モバイルChrome双方で確認）
- [ ] 東京リージョン (ap-northeast-1) にデプロイされ、本番ドメインで公開されている
- [ ] CloudWatch ダッシュボードで主要メトリクス（音声入力成功率、エラー率、レイテンシ）が観測できる
- [ ] プライバシーポリシー／利用規約ページが整備されている（個人情報の取扱明示）
- [ ] Googleログインが本番OAuth設定で動作する
- [ ] Chrome以外のブラウザアクセス時、利用不可の案内が表示される
- [ ] ステークホルダーによるレビューと承認が完了している

## Risks and Dependencies

### Key Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Amazon Bedrock の Claude モデルが東京リージョンで未提供／レイテンシが大きい | High | High | クロスリージョン推論プロファイル利用、または Bedrock 呼出のみ別リージョンを許容 |
| Web Audio API + Transcribe Streaming の音声入力でChromeのマイク権限まわりがブロッカーになる | Medium | High | テキスト入力フォールバックを Must Have で確保 |
| iOS Chrome はWebKitベースで Web Audio／マイク権限の挙動がデスクトップChromeと異なる | Medium | High | iOS Chromeでの早期実機検証、必要に応じてファイル入力（録音→アップロード）等の代替フローを追加検討 |
| 「全肯定」メッセージが本当に有害な意思決定（健康・依存症等）まで肯定してしまい、ユーザーに害を与える | Medium | High | LLMプロンプトでガードレールを定義（健康・医療・依存に関わるやめ候補は肯定トーンを抑え注意喚起する） |
| Googleログイン必須化により、Googleアカウントを持たないユーザーが離脱する | Medium | Medium | ターゲット層はGoogleアカウント保有率が高いと想定。Phase 2でApple／メール認証／パスキー等の追加IdP導入を検討 |
| Google OAuth クライアントの本番審査で Sensitive scope を要求された場合に審査が長期化 | Low | Medium | MVPではメールアドレスとプロフィールの基本スコープのみ要求し、Sensitive／Restricted scope は使用しない |
| 個人の支出・悩みが入力されるためプライバシー懸念がある | Medium | High | 入力データの保存最小化、暗号化、明示的なプライバシーポリシー |
| Bedrock／Transcribe のコストが想定を超える | Medium | Medium | 1ユーザーあたりの呼出回数上限を設定、CloudWatch アラーム |
